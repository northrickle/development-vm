## Documentation

Apply these rules when creating, editing, or reviewing documentation. Present the big picture first, then organize the details for scanning and later reference.

### Structure

- Apply **progressive disclosure**: overview first, details last.
- Start with purpose, context, key facts, and conclusions.
- Follow with components, steps, decisions, or dependencies; defer implementation details and explanations.
- Allow multiple overview levels, each independently useful.
- Adapt sections to the document type; omit unnecessary ones.
- Separate **WHAT** (facts/actions/decisions), **HOW** (implementation), and **WHY** (rationale).

### Formatting

- **Never nest lists.** Use headings for hierarchy.
- Keep headings, paragraphs, and list items short and focused.
- Use numbered steps for procedures, checklists for tasks, bullets for facts.
- Use tables for comparisons and diagrams for relationships or flows when helpful.
- Use language-tagged code blocks for code, commands, and configuration.
- Highlight critical decisions, constraints, warnings, and success criteria sparingly.
- Avoid walls of text, repetition, decoration, and unnecessary introductions.
- Follow GitHub/Obsidian Markdown conventions.

### Content

- Optimize for scanning and quick information retrieval.
- Be concise, precise, and actionable.
- Include prerequisites, context, and expected outcomes where relevant.
- Document important dependencies, constraints, trade-offs, and decisions.
- Include verification, diagnostics, and risks when applicable.
- Never invent missing information; label assumptions and unknowns.
- Keep documentation self-contained and useful after long periods.
- Link authoritative sources instead of duplicating lengthy or volatile information.

**Core principle:** Big picture first, details later. Readers should be able to stop at any level of detail without losing essential context.
